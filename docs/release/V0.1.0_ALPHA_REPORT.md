## Delivered product path

The alpha keeps the validated RunBack flow intact:

```text
failed GitHub Actions run URL
  -> GitHubOnlineSource
  -> canonical RunEvidence
  -> existing Resolver and Replay Plan
  -> ActExecutor
  -> Matcher
  -> SAME_FAILURE
  -> session / dev / replay --step / verify
```

The release-stage implementation added only the public entry surface and one general network
regression fix exposed by the clean-machine test. M1, M2, Direct URL identity, Matcher
thresholds and historical results were not redesigned.

## Doctor and version

`runback version` and `runback --version` report `RunBack v0.1.0-alpha` in the release build.
`runback doctor` checks Git, Docker CLI, Docker daemon, act, GitHub API access, the short
workspace allocator and Docker network reachability. It reports problems and performs no
installation, daemon restart, bridge repair, firewall change or host-network change.

GitHub authentication remains optional for public repositories, with priority:

```text
RUNBACK_GITHUB_TOKEN > GH_TOKEN > anonymous
```

## Managed network regression

The clean replay exposed a general fault: RunBack's earlier selector could reuse an existing
managed bridge after only checking its label, even when that bridge no longer had TCP 443
reachability. The selector now probes both the Docker default bridge and any existing
RunBack-managed bridge. If neither works, it creates at most one bridge named
`runback-managed`, with `io.runback.managed=true`, Docker's default IPAM and no fixed subnet
or gateway. It probes the new bridge before execution.

The implementation never deletes or rebuilds `docker0`, edits Docker daemon configuration,
restarts Docker, changes the host IP, firewall or routing table, or selects a network by
repository name. The final clean replay recorded `Network Source: MANAGED_FALLBACK`.

## Known alpha limits

The alpha targets completed failed runs in public repositories, `ubuntu-latest`, and common
JavaScript/TypeScript, Python and Go workflows that act can approximate. It does not claim
support for private repositories, GitHub Enterprise, self-hosted/Windows/macOS runners,
secret-heavy workflows, services, complex container or local actions, or perfect recovery of
the original hosted runner. A blocked or different failure remains a valid truthful result.

## External-user launch

The public release was followed by a 100-entry candidate scan. Thirty open human-authored PRs
with a specific failed Ubuntu job were retained after removing obvious preview, AI-review,
label and aggregate-check gates. Fifteen tailored first-wave comments were posted successfully
across distinct repositories. At the later checkpoint, six still-open and relevant reserve
cases received a second-wave comment; closed and out-of-scope reserve cases were withheld.
All 21 comments link the recipient's exact failed run and ask for truthful alpha results without
asking for a star.

Initial observed counts are 0 replies, 0 installations and 0 external RunBack executions, so
the user-validation state is `USER_VALIDATION_PENDING`. Candidate evidence and every outreach

`docs/users/EXTERNAL_USER_REPORT.md`.

To add an opt-in public entry point without sending unsolicited mass comments, GitHub
Discussions was enabled and an alpha testing announcement was published at
https://github.com/huanglinfei091-cmd/runback/discussions/1. The English and Chinese READMEs
link to that discussion. Channel-specific Show HN, Reddit DevOps and DEV Community drafts are
stored in `docs/launch/`; they are not recorded as published because no authenticated
submission was made on those services.

The public distribution goal is reach, not a claim of 1,000 contacted people. Views, release
downloads, stars and reactions remain separate from verified testers. The direct-outreach
total stays at 21, below the existing daily cap of 30, and the validation state remains
`USER_VALIDATION_PENDING` until an external person reports a concrete RunBack invocation or
equivalent execution evidence.
